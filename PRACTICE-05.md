Перед імпортом потрібні завершений тег `practice-04`, чистий робочий каталог
і працездатні власні попередні тести. `origin` — ваш форк, `upstream` —


Якщо `upstream` ще немає, додайте його один раз:
`git remote add upstream https://github.com/serhii-ch-eu/digital-dean-api-starter.git`.
За конфлікту зберігайте власні реалізації та попередні маршрути. Не
застосовуйте `reset` або `--allow-unrelated-histories` для імпорту каркаса.
Python 3.12+ і SQLite 3.24.0+; модулі sqlite3, hashlib, secrets і hmac входять до стандартної
бібліотеки. FastAPI, Pydantic з email-validator, Uvicorn та pytest уже належать
до залежностей проєкту; додатковий сервер бази й ORM не потрібні.

## Що реалізувати

1. `app/db/initialize.py`: атомарне створення шести таблиць із
   `DDL_STATEMENTS` і точних довідників `STATUS_ROWS`, `ROLE_ROWS`. Повторний
   запуск не дублює довідники й не видаляє користувачів. За невідповідності
   наявного довідника — відмова і rollback, не непомітне виправлення даних.
2. `app/security/passwords.py`: `make_password_record`, `verify_password`.
3. `app/repositories/user_repository.py`: чотири операції з короткими
   окремими з'єднаннями, параметризованим SQL і транзакціями.
4. `app/api/accounts.py`: декоратори та тіла `register_user`, `delete_user`,
   `block_user`, `login`; підключення `router` до **наявного** `app/main.py`.
5. Власні додаткові негативні тести, перевірку перезапуску, Postman та звіт.
   Версію того самого API і метадані проєкту оновіть до `0.5.0`.

Початкові TODO навмисно не реалізовані. Вони мають бути замінені власним
кодом; видалення тестів або приховування їх через skip/xfail не є виконанням.
Наданий ізольований приклад працює без TODO, не створює файл чи обліковий запис.

## Схема й довідники

Колонки збережені точно: `status(id,name)`,
`user(id,name,email,login,password,salt,status_id)`, `role(id,name)`,
`user_role(user_id,role_id)`, `course(id,name)`,
`grade(student_id,teacher_id,course_id,grade)`.
Типи — INTEGER або TEXT відповідно до завдання. `password` означає запис
алгоритму/параметрів/хешу, ніколи відкритий пароль.

Статуси: `(0,"inactive"),(1,"active"),(2,"blocked")`.
Ролі: `(1,"admin"),(2,"manager"),(3,"teacher"),(4,"student")`.
Ролі й статуси не взаємозамінні. Роль під час реєстрації автоматично не
призначається; привілейовані поля клієнта заборонені. Зв'язки `user_role`
створюють у локальних тестових фікстурах для перевірки обмежень.

`user_role` має ключ `(user_id,role_id)` і каскадне видалення лише зв'язків
видаленого користувача. `grade` має ключ `(student_id,course_id)` і оцінку
0..100 — локальна шкала цієї роботи. Обидва посилання на користувачів і
посилання на курс мають `ON DELETE RESTRICT`. Зовнішній ключ гарантує
існування користувача, але сам по собі не перевіряє роль teacher/student.
Тут немає CRUD курсів/оцінок, автоматичної міграції старих студентів чи
ототожнення їх UUID із новими цілими id облікових записів.

Наданий `open_database` установлює `PRAGMA foreign_keys=ON` і перевіряє його
на кожному з'єднанні до початку транзакції. `autocommit=True` обрано явно;
`write_transaction` виконує SQL `BEGIN IMMEDIATE`, `COMMIT` і `ROLLBACK`.
Не замінюйте їх `connection.commit()`/`rollback()` або `with connection`
у цьому режимі; не використовуйте `executescript` усередині цієї транзакції.
Не створюйте спільне з'єднання для різних потоків і не вимикайте перевірку FK.

## Фіксований парольний профіль

PBKDF2-HMAC-SHA256, 600000 ітерацій, 16 випадкових байтів солі, 32 байти
результату. `salt` — 32 символи lowercase hex.
`password` — `pbkdf2_sha256$600000$<64 lowercase hex chars>`.
Перевіряйте весь формат і дозволений профіль перед обчисленням; не довіряйте
довільній кількості ітерацій із бази. Порівнюйте фіксовані двійкові результати
через `hmac.compare_digest`, не відкриті паролі або їх швидкий одиничний хеш.

Реєстрація: пароль 15..128 символів Unicode, до 512 байтів точного UTF-8,
без нульового символу; пробіли й регістр зберігаються. Це локальний профіль,
не повна виробнича парольна політика і не сертифікація. У запиті login
приймається 1..128 символів із тією самою байтовою межею; неправильний короткий
пароль має дати false, а не вважатися новою реєстрацією. `login` під час
реєстрації — `[a-z][a-z0-9_.-]{2,31}`; email проходить EmailStr і casefold
як явне локальне правило унікальності, а не універсальна властивість email.

## Контракт API

| Функція | Метод і шлях | Успіх | Основні відмови |
|---|---|---|---|
| register_user | POST /api/v1/users | 201, id/name/email/login/status_id | 409 duplicate; 422 input |
| delete_user | DELETE /api/v1/users/{user_id} | 204, порожнє тіло | 404 missing; 409 grade reference |
| block_user | PATCH /api/v1/users/{user_id}/block | 200, ті самі публічні поля, status_id=2 | 404 missing; 422 invalid id |
| login | POST /api/v1/auth/login | 200, JSON boolean true/false | 422 malformed input |

За відсутності status_id застосовується **0**, явно дозволені лише цілі
0,1,2; bool, float, рядок і null не є коректним статусом. `login` повертає
true лише для правильного логіна/пароля **та status_id=1**. Для inactive,
blocked, невідомого логіна, хибного пароля чи пошкодженого запису — false.
Це не сесія, токен чи авторизація адміністративних операцій. Синтаксично
неправильне тіло й невідповідність схемі відрізняйте від хибних облікових даних.

Для блокування повторний запит повертає 200 і не змінює решту даних.
Видалення за посиланням grade заборонено для студента й викладача; rollback
має зберегти користувача, оцінку і зв'язки ролей. Непов'язаний користувач
фізично видаляється, його user_role каскадно зникають. Не видаляйте оцінки.

Контрольовані detail: `user already exists` (409), `user not found` (404),
`user has grade references` (409), `database unavailable` (500).
Помилки валідації очищує наданий `SensitiveRoute`, якщо ви використали
готовий router; не повертайте input/ctx/body, SQL, шлях чи текст винятку.
Не застосовуйте `SELECT *` для публічної відповіді. `UserPublic` не містить
password/salt. Прив'язуйте всі зовнішні значення до параметрів `?`.

## Запуск і перевірки

Працюйте у власному активованому віртуальному середовищі попередніх робіт.
Після реалізації:

```bash
python -m app.db.initialize
python -m app.db.initialize
python -m pytest
python -m uvicorn app.main:app --host 127.0.0.1 --reload
```

Робоча база — `var/digital-dean.sqlite3`. Тести використовують tmp_path і
підміну залежності репозиторію, ніколи робочу базу. `var/.gitignore` виключає
базу й усі її sidecar-файли. `/health` зберігає попередній контракт і не
доводить готовності SQLite. Перевірку перезапуску проведіть окремо: створіть
вигаданий active-акаунт, завершіть сервер, знову запустіть із тією самою базою
і перевірте login; потім заблокуйте й повторіть. Не стирайте базу між кроками.

Імпортуйте `postman/digital-dean-practice-05.postman_collection.json`.
Змінна base_url — `http://127.0.0.1:8000`. Запускайте основну послідовність
з початку; вона генерує нові синтетичні логіни й очищає лише створені нею
непов'язані акаунти. Сценарій навмисного збою бази не запускайте на чужому
сервері; такий випадок перевіряють pytest на тимчасовому каталозі.

Додайте власні тести FK, rollback, двох з'єднань, незмінності блокованого
пароля, безпечних 422/500, перезапуску та всіх попередніх реалізованих шляхів.
Надані тести — початковий мінімум, не доказ повноти або продуктивності.

документі практичної використовується глосарій наприкінці, а не виноски.

обліковими даними. Результат тесту не вигадуйте.

в Інтернет. Наявність солі чи compare_digest не усуває всіх загроз входу.
