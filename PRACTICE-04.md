# Практична робота 4 — алгоритми хешування

Розширюйте **свій завершений API практичних 1–3** у тому самому форку й клоні.
Це стартовий каркас, а не готовий розв'язок. Інструкція та критерії наведені у DOCX.

## Імпорт зі збереженням історії

Перед імпортом: завершений тег `practice-03`, чистий робочий каталог, попередні
тести проходять. `origin` — власний форк, `upstream` — викладацький репозиторій.

```bash
git status --short
git remote -v
git fetch upstream
git switch -c practice-04 practice-03
git merge --no-ff upstream/practice-04-starter -m "Import practice 4 scaffold"
git tag -a practice-04-base -m "Practice 4 imported baseline"
python examples/practice_04_hash.py
```

Якщо `upstream` ще не налаштований, додайте його один раз:
`git remote add upstream https://github.com/serhii-ch-eu/digital-dean-api-starter.git`.
Не клонуйте другий непов'язаний проєкт, не використовуйте `reset` або
`--allow-unrelated-histories`. За конфлікту збережіть свої попередні реалізації,
інтегруйте нові файли й повторіть тести. Нових бібліотек для хешування не потрібно:
`hashlib` є частиною Python 3.12+. Наявні залежності та маршрути не видаляйте.

## Що реалізувати

1. `prepare_operation` і `hash_bytes` у `app/security/hashing/adapters.py`:
   whole і chunked, новий об'єкт на кожне повідомлення. Підготовлена операція
   повертає викличний об'єкт без аргументів; він щоразу створює новий стан,
   виконує `update` готових блоків і повертає `digest`. Блоки готуйте один раз
   поза таймером, не всередині кожного повтору `hash_bytes`.
2. `hamming_bits`: кількість відмінних бітів двох непорожніх хешів однакової
   довжини, не кількість відмінних символів шістнадцяткового запису.
3. `validate_report` у `app/schemas/hash_report.py`: структура та повне змістове
   покриття. Не вилучайте діагностичні перевірки з `passed=False`.
4. `benchmarks/hash_benchmark.py`: локальний експеримент, сирі CSV, перевірений
   JSON; жодних вимірювань у обробнику HTTP.
5. Новий `GET /api/v1/lab/crypto/hash-benchmark-results` із `HashResponse` та
   підключення його маршрутизатора до **наявного** `app/main.py`.
6. Власний варіант, тести, Postman і документацію. Версія того самого API — 0.4.0.

## Фіксований експеримент

Профілі: sha256, sha512, sha3-256, blake2b-256, blake2s-256, md5, sha1.
BLAKE2 використовує `digest_size=32`, а не обрізання готового результату.
MD5/SHA-1 мають лише неза́хисне навчальне призначення. Якщо середовище їх не
надає, збережіть явний статус недоступності, без вимірювань, нулів чи зміни
політик безпеки. Недоступність основного профілю — помилка передумов запуску.

Розміри: 64, 1024, 65536, 1048576 байтів. Два режими: whole і chunked.
Прогрів: 10 операцій; 5 серій по 1000 операцій для перших трьох розмірів,
по 100 для 1 МіБ. Медіана та IQR за `quantiles(..., method="inclusive")`.
Таймер охоплює створення об'єкта, `update`, `digest` і цикл, але не підготовку
даних, нарізання блоків, перевірки, перетворення в hex або файлові операції.

Лавинний ефект: 100 окремих змін по одному біту початкових 1024 байтів.
У досліді i змінюйте біт i для i=0..99, щоразу у новій копії оригіналу;
біт i має маску `1 << (i % 8)` у байті `i // 8`. Обчисліть відстані й частки.
Не встановлюйте порогу «безпечності» та не вважайте це доказом стійкості.

Для A доступних профілів: 8A агрегатів швидкодії, 40A рядків raw.csv,
A агрегатів та 100A рядків avalanche.csv, 6A перевірок коректності.
Коли доступні всі сім: відповідно 56, 280, 7, 700, 42.

## Варіант за остачею номера студента від ділення на 4

- 0: фільтр `algorithm` за явним переліком семи ідентифікаторів;
- 1: фільтр `payload_bytes` за переліком чотирьох розмірів;
- 2: фільтр `mode` зі значеннями whole/chunked;
- 3: `summary` з algorithms_count, available_count, results_count,
  checks_count, all_checks_passed. Недоступний профіль не є проваленою перевіркою.

Для фільтра: відсутній параметр означає всі результати; невідоме значення — 422.
Запит недоступного, але відомого алгоритму повертає 200 із порожнім results
та збереженим статусом. Спершу валідуйте весь файл як HashReport, потім
формуйте HashResponse. Поля algorithms/avalanche/checks лишаються повними.

## Запуск і подання

Працюйте у власному активованому віртуальному середовищі попередніх робіт.

```bash
python -m pytest
git status --short
git rev-parse HEAD
python -m benchmarks.hash_benchmark
python -m uvicorn app.main:app --reload
```

Перед експериментом зафіксуйте код і забезпечте чистий робочий каталог.
Збережіть source_commit саме цього запуску; він має бути предком фінального тегу.
Результати створюєте власноруч: `results/practice-04/raw.csv`, `avalanche.csv`,
`report.json`. Фікстури в тестах — не виміряні результати й не можуть їх замінити.

HTTP: 200 валідний звіт, 404 відсутній, безпечний 500 некоректний, 422 поганий
параметр вашого фільтра. Фіксований серверний шлях, обмежене читання, жодних
секретів або справжніх документів. Зміни додають до того самого API.

У колекції Postman встановіть variant=0..3 і залиште manual_state порожнім
для звичайного запуску. Після резервної копії локального звіту можна окремо
виконати один ручний запит зі значенням manual_state=missing або invalid.
Не запускайте всю колекцію, коли файл навмисно відсутній чи пошкоджений;
після перевірки відновіть його.

Після baseline потрібні щонайменше чотири власні змістові комміти: адаптери;
експеримент і схема; API та варіант; тести й документація. Імпорт не рахується.

```bash
git log --oneline practice-04-base..HEAD
git merge-base --is-ancestor practice-03 HEAD
git push -u origin practice-04
git tag -a practice-04 -m "Practice 4 verified result"
git push origin tag practice-04-base
git push origin tag practice-04
```

Додатково перевірте `git merge-base --is-ancestor`, передавши фактичний
source_commit зі звіту як перший аргумент та HEAD як другий.
Подайте власний форк, гілку, теги, тести, Postman, обидва CSV, JSON, щонайменше
два графіки й звіт за `docs/practice-04-report-template.md`. Стартові TODO
мають бути реалізовані; видалення тестів, skip/xfail або підміна вимірювань
готовою фікстурою не відповідають завданню.
